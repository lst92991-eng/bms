# BMS 项目文档写作 Skill

适用范围：本仓库 BMS/UPS 类项目文档、架构说明、硬件软件映射、bring-up 记录、评审说明。

使用要求：每次写作或修改本项目文档前，先读本文件，再读 `AGENTS.md`。如果本文件与 `AGENTS.md` 冲突，以 `AGENTS.md` 为准；如果本文件与当前源码/网表/PDF 冲突，以当前证据为准，并在文档中写 `Conflict`。

## 写作目标

1. 让读者先知道项目是什么，再知道为什么这样设计。
2. 每个硬件结论都落到 PDF/网表/CubeMX/代码中的至少一个证据。
3. 每个软件结论都落到源码、构建脚本、`.ioc`、启动文件或既有规则文档中的行号。
4. 旧项目只作为文档标准和风格来源，不作为新项目芯片寄存器、阈值、引脚连接的事实来源。
5. 不补假图，不补假测试，不补没有证据的功能状态。
6. 正文要像旧 Word 的项目讲义，不像审计报告：先讲“为什么这样做”，再讲“硬件怎么连”，最后讲“代码怎么写”。证据、Unknown、Conflict 可以保留，但应放在每节末尾或附录，不能让正文被矩阵和置信度打断。

## 写作口吻与正文密度

- 一章只解决一个学习问题，例如“如何让 BQ76952 先安全复位并读到设备号”，不要把所有证据一次性堆成表。
- 每个芯片章节按旧文档节奏写成：芯片作用 -> 本项目连接方式 -> CubeMX/工程配置 -> INT 层接口 -> APP 层调用 -> 调试入口。
- 表格只用于真正需要比较或查找的地方。普通解释、初始化流程、代码思路优先用短段落、编号步骤和代码块。
- 代码块必须来自当前源码的关键片段或是等价的流程摘录，并在代码块前后标明来源行号；不能写“示例代码”冒充当前实现。
- 图位要穿插在对应讲解处：硬件图放硬件章，CubeMX 图放配置章，串口/波形图放 bring-up 章。没有真实图时保留固定格式 TODO。
- “Evidence Index / Unknowns / Conflicts”是合规兜底，放在文末；正文中只保留简短“出处”。

## 文档结构模板

推荐正文顺序：

1. 项目概述
2. BMS 与本项目需求
3. 本项目总体架构
4. 项目基础搭建：CubeMX、Keil/CMake、FreeRTOS
5. BQ76952 电池监控芯片
6. BQ76952 接口层：唤醒、CRC、读写与 Data Memory
7. BQ76952 APP 层：配置、采样、SOC/SOH、均衡、FET
8. SC8815 充电控制芯片
9. SC8815 接口层与充电请求状态机
10. 电源状态机：BQ 与 SC8815 如何协同
11. OLED、EEPROM、FDCAN 与串口诊断
12. Bring-up 顺序与必须补图
13. Unknowns
14. Conflicts
15. Evidence Index

如果写的是短文档，可以缩小章节，但不能删掉 `Unknowns`、`Conflicts`、`Evidence Index`。

## 证据写法

每个非平凡结论使用这个最小格式：

```text
结论：...
证据：path/to/file:line 或 Word 文件段落/PDF 页号/网表行号
置信度：High/Medium/Low
人工确认：Needed/Not needed
```

证据优先级：

1. 当前源码、`.ioc`、CMake/Keil 工程、启动文件、链接脚本。
2. 当前网表 CSV 与当前 PDF 原理图。
3. 当前 `docs/rules/` 和 `docs/logic/` 中已经固化的项目规则。
4. 官方芯片资料。
5. 旧项目 Word/代码，只用于写法、章节顺序、旧逻辑对照。

缺失证据时写 `Unknown`。冲突证据必须写成 `Conflict`，不能合并成一个看起来圆满的结论。

## 图像规则

旧文档图像密度很高，新文档也应当保留关键图位。图像分三类：

| 图像类型 | 处理规则 |
| --- | --- |
| PDF 原理图截图 | 能用 Poppler/截图工具稳定生成时，放入 `docs/wordflow/assets/` 并在正文标注来源 PDF 和页号。 |
| CubeMX/Keil 配置截图 | 能直接打开工具并截图时放入 assets；如果工具不可用，写 `//TODO 此处应该放 CubeMX xxx 配置图`。 |
| 实测波形、串口、示波截图 | 没有真实测试就只能写 TODO，禁止生成示意图冒充实测图。 |

TODO 格式固定：

```text
//TODO 此处应该放 <具体图名>，用于证明 <要证明的事实>。当前可引用的文字证据是 <path:line>。
```

## 旧 Word 风格提炼

旧文档的有效写法：

- 先写业务背景，再写本项目选型，避免读者直接陷入代码。
- 芯片章节先讲能力和引脚，再讲 CubeMX/Keil 配置，再讲接口层代码。
- BQ 章节按“唤醒/CRC/读写/配置/采样/保护/均衡/FET”推进，适合 BMS 初学者。
- 每个算法章节先讲策略，再放代码接口，再说明测试入口。
- 通信章节先定义命令和数据格式，再讲底层发送/接收，再讲 APP 调用。

新项目必须调整的地方：

- BQ76952 使用 direct command、subcommand、Data Memory、transfer buffer checksum，不能沿用 BQ76930 单字节寄存器讲法。
- 当前项目有 SC8815 和 BQ76952 双芯片协同，必须单独写两条链路。
- 当前项目已有 FreeRTOS 任务入口，不能沿用旧蒸馏文档中的 bare-metal 结论。
- 当前项目需要把硬件风险和待实测项前置，尤其是 SC8815 VBATS 分压、BQ CC2 电流方向、温度资源、FET 实际状态、均衡热验证。
